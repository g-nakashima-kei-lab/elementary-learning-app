# 100マス計算アプリ　データ設計書

**版：基本構想 v1.3**

## 1. データ設計の基本方針

全国の学校で利用することを想定し、学校ごとにデータを分離する。

データは、学校・先生・クラス・問題セット・配布・児童・解答結果の関係で管理する。

重要なのは、画面に表示する名前や番号と、システム内部でデータを識別するIDを分けることである。

内部IDにはUUIDなどの重複しにくい識別子を使用する。

## 2. データの関係

```text
学校（School）
 ├─ 先生（Teacher）
 └─ クラス（Class）
      ├─ 児童（Student）
      └─ 配布（Assignment）
           ├─ 問題セット（ProblemSet）
           └─ 解答結果（Attempt）
                └─ 児童（Student）
```

先生は担当する学校・クラスの範囲で管理する。学校をまたいでデータを閲覧できないようにする。

## 3. 管理するデータ

### ① 学校（School）

| 項目 | 内容 |
|---|---|
| school_id | 学校の内部ID |
| school_name | 学校名 |
| school_type | 公立・私立など |
| created_at | 登録日時 |
| status | 利用状態 |

### ② 先生（Teacher）

| 項目 | 内容 |
|---|---|
| teacher_id | 先生の内部ID |
| school_id | 所属学校ID |
| email | ログイン用メールアドレス等 |
| display_name | 表示名 |
| role | 管理者・先生など |
| status | 利用状態 |

先生の認証情報やパスワードは、独自に平文で保存しない。認証サービスを利用する。

### ③ クラス（Class）

| 項目 | 内容 |
|---|---|
| class_id | クラスの内部ID |
| school_id | 所属学校ID |
| grade | 学年 |
| class_name | クラス名 |
| school_year | 年度 |
| created_at | 登録日時 |
| status | 利用状態 |

クラス名は学校ごとに重複する可能性があるため、クラス名だけで識別しない。

### ④ 児童（Student）

| 項目 | 内容 |
|---|---|
| student_id | 児童の内部ID |
| class_id | 所属クラスID |
| attendance_number | クラス内の出席番号 |
| school_year | 在籍年度 |
| created_at | 登録日時 |
| status | 在籍・利用状態 |

当初は児童の氏名、メールアドレス、生年月日などを登録しない。児童はログインせず、課題URLからクラスを自動判定し、画面に表示された出席番号ボタンから番号を選択する。サーバー側では、assignment_idからclass_idを特定し、class_id・school_year・attendance_numberの組み合わせで児童レコードを特定して、内部のstudent_idで結果を結び付ける。出席番号だけを全校共通の識別子として扱わない。同じ年度・クラス内で出席番号が重複しないよう制約を設ける。

クラスと出席番号は、学校内で児童を識別できる場合がある。氏名を保存しなくても個人に関係する情報として扱い、実際の児童データを使う前に必要な承認・安全対策を確認する。入力値のなりすましを完全には防げないため、児童入力は本人確認ではなく記録の紐付け手段と位置付ける。

### ⑤ 問題セット（ProblemSet）

| 項目 | 内容 |
|---|---|
| problem_set_id | 問題セットの内部ID |
| school_id | 作成した学校ID |
| created_by | 作成した先生ID |
| display_number | 画面に表示する問題セット番号 |
| operation | ＋・－・×など |
| grid_size | 5×5・10×10など |
| difficulty | 難易度 |
| generation_type | 共通・ランダムなど |
| problem_data | 問題内容または再現に必要な情報 |
| created_at | 作成日時 |
| version | バージョン |

表示番号が同じでも、内部IDが異なれば別の問題セットとして扱う。

### ⑥ 配布（Assignment）

| 項目 | 内容 |
|---|---|
| assignment_id | 配布の内部ID |
| school_id | 学校ID |
| class_id | 配布先クラスID |
| problem_set_id | 使用する問題セットID |
| teacher_id | 配布した先生ID |
| assignment_name | 配布名 |
| access_token_hash | 児童用URLトークンのハッシュ値（平文トークンは保存しない） |
| snapshot_data | 配布時点の問題内容 |
| start_at | 開始日時 |
| end_at | 終了日時 |
| status | 公開・終了など |

配布は、問題セットとは別のデータとして管理する。

同じ問題セットを2つのクラスに配布する場合は、2つのAssignmentを作成する。

配布後に問題セットを編集しても、配布済みの問題内容は変わらないようにする。

### ⑦ 解答結果（Attempt）

| 項目 | 内容 |
|---|---|
| attempt_id | 解答記録の内部ID |
| school_id | 学校ID |
| class_id | クラスID |
| assignment_id | 配布ID |
| problem_set_id | 問題セットID |
| student_id | 児童ID |
| started_at | 開始日時 |
| completed_at | 終了日時 |
| elapsed_ms | 所要時間 |
| correct_count | 正解数 |
| total_questions | 問題数 |
| accuracy_rate | 正答率 |
| incorrect_count | 誤答数 |
| unanswered_count | 未回答数 |
| correction_count | 訂正回数 |
| created_at | サーバー受信日時 |
| is_valid | 集計対象として有効か（初期値true） |
| invalidated_at | 無効化日時（無効化時） |
| invalidated_by | 無効化した先生ID（無効化時） |
| invalidation_reason | 無効化理由（無効化時） |
| submission_id | 再送による二重登録を防ぐ一意な送信ID |

解答結果は原則として追加保存する。新しい結果で過去の結果を上書きしない。

同じ児童が同じ課題に複数回取り組んだ場合も、それぞれ別のAttemptとして記録する。

## 4. データの識別ルール

- 学校：school_id
- 先生：teacher_id
- クラス：class_id
- 児童：student_id
- 問題セット：problem_set_id
- 配布：assignment_id
- 解答：attempt_id

表示番号やクラス名、児童の出席番号だけでデータを結び付けない。

## 5. 児童ログインなしでの識別方法

第1段階では児童アカウントを作らない。課題URLによりクラスを自動判定し、児童は出席番号のみを選択する。

1. 先生が年度・学年・クラスを登録する。
2. クラスに在籍する出席番号（氏名は初期版では登録しない）を設定する。
3. 先生が課題を作成し、推測困難なランダムトークンを含む課題URLを発行する。
4. 児童は課題URLを開く。サーバーはトークンからassignment_idとclass_idを特定する。
5. 対象クラスで有効な出席番号だけをボタン表示し、児童は計算開始前に自分の番号を選択する。
6. サーバーは当該課題・クラスに属する番号かを検証し、内部student_idに対応付ける。
7. 解答結果をAttemptとして保存する。
8. 同じ年度・クラス・出席番号の履歴を時系列で集約する。

課題URLのトークンは十分な長さの暗号学的乱数で生成し、連番やclass_idをそのままURLに含めない。トークンはサーバー側で照合し、終了・無効化できるようにする。トークンを知る人は課題にアクセスできるため、本人確認の代わりにはならない。児童画面にはクラス全員の結果や他児童の履歴を返さない。

出席番号の入力は本人確認ではない。他人の番号を入力できる可能性があるため、結果の訂正・再紐付け手順を用意する。児童用画面やAPIから、他の児童の履歴一覧を取得できない設計とする。

## 6. 学校間のデータ分離

全国で利用する場合、学校間のデータ分離は必須とする。

- すべての学校所属データにschool_idを持たせる。
- サーバー側でアクセス権限を確認する。
- 画面上で他校のデータを隠すだけの対策にしない。
- 先生が所属していない学校のデータを取得できないようにする。
- 児童用URLから取得できる情報を必要最小限にする。

## 7. 先生用の結果出力

先生が認証後、担当クラスの範囲で、選択した課題（Assignment）単位の解答結果をCSV出力できるようにする。初期版ではCSVを優先し、Windows版Excelで扱いやすいUTF-8 BOM付きとする。出席番号の昇順で出力する。出力はサーバー側で先生の権限・対象クラス・対象課題を確認してから生成する。児童用URLや児童側の画面からクラス全員分のデータを取得できないようにする。クラス全期間の一括出力は初期版の対象外とする。

出力項目：年度、学年、クラス、出席番号、課題名、問題セット（表示番号または識別用名称）、実施日時、所要時間、正解数、問題数、正答率、誤答数、訂正回数。01_全体設計書のCSV項目と一致させる。氏名は初期版では出力しない。無効化されたAttemptは通常のCSV出力・集計から除外する。

## 8. データ保存・削除方針

実装前に次のルールを決める。

- 学校が利用を終了した場合のデータの扱い
- 児童の転校・進級・クラス替えへの対応
- 出席番号の変更・転出入・進級時の履歴引継ぎ
- 解答結果の保存期間
- 先生の異動・退職時のアカウント管理
- 誤登録や不正アクセスが発生した場合の対応
- 学校からデータ削除を求められた場合の手順

保存期間は一律に決め打ちせず、学校・自治体のルールや利用目的を確認して定める。

## 9. 将来の拡張

将来、児童ログインを導入する場合も、AttemptやAssignmentの基本構造は維持できるようにする。

将来、正式な児童アカウントを導入する場合は、本人確認と既存履歴の安全な紐付け手順を設計する。

Google Classroom連携などを追加しても、問題セット・配布・解答結果の関係は維持する。


## 10. Phase 1の追加データ・制約

### 課題URLトークン

- `access_token`は十分な長さの暗号学的乱数で生成する。
- URLトークンから学校ID・クラスID・出席番号などを推測できない形式にする。
- データベースにはトークンそのものを保存せず、暗号学的に安全なハッシュ値を保存する。発行時に表示・配布する平文トークンは再表示できない扱いとし、紛失時は再発行して旧トークンを失効させる。
- 課題の終了・停止・再発行時に旧トークンを無効化できるようにする。
- トークンはアクセス手段であり、児童本人を認証するものではない。

### 出席番号ボタン

- 表示する番号は、課題の対象クラスで有効な番号に限定する。
- 先生がクラス人数を入力すると1から人数までを自動生成し、必要に応じて個別に有効／無効を変更できる。番号の範囲を一律に1〜40と固定しない。
- 氏名や他児童の結果は児童画面に表示しない。
- 誤選択・誤送信に備え、先生がAttemptを削除せず無効化できるようにする。無効化理由・日時・操作した先生IDを記録し、通常の集計・CSVから除外する。別児童への再紐付けはPhase 1のUI対象外とし、必要時は管理者の個別対応とする。

### 学年・年度・クラス替え

Phase 1では、児童レコードの識別を年度・クラス・出席番号の範囲に限定する。進級・クラス替え後に同一人物として自動的に履歴を統合しない。継続的な個人履歴を学校の正式な運用で扱う場合は、本人確認・引継ぎ・訂正手順を別途設計する。

### 先生認証・データアクセス

初期試作ではメールアドレス＋パスワード方式を第一候補とし、認証情報は認証サービスに管理させる。独自に平文パスワードを保存しない。Supabaseを第一候補として検証するが、正式採用前に費用・アクセス制御・バックアップ・データ保管条件を確認する。

先生用画面を`teacher.html`として分離しても、それ自体はアクセス制御にならない。先生用API・データ取得・CSV出力のすべてで、サーバー側が認証と担当学校・クラスの権限を検証する。ブラウザ側にサービスロールキー等の秘密情報を置かない。


## 11. Phase 1のサーバー関数・権限制御

### 児童からの解答送信

児童用ブラウザからAttemptテーブルへの直接INSERT権限は与えない。Phase 1ではSupabase Edge Functionを第一候補として、次の処理をサーバー側で行う。

1. 課題トークンを受け取る。
2. トークンのハッシュ値を照合し、有効な課題・対象クラスを特定する。
3. 課題の公開状態・期間を検証する。
4. 出席番号が対象クラスで有効か検証し、内部student_idを特定する。
5. 解答データの型・範囲・サイズを検証する。
6. レート制限等を適用し、submission_idによる重複送信を検出する。
7. 検証に通った結果だけをAttemptとして保存する。

サービスロールキー等の秘密情報はEdge Function等のサーバー環境にのみ保存し、ブラウザへ送らない。RPCを採用する場合は、実行権限、RLSとの関係、SECURITY DEFINERの利用有無と安全性を実装前レビューで確認する。サーバー関数を設けても、トークン共有によるなりすまし・大量送信を完全には防げないため、レート制限・監視・課題トークン失効手段を設ける。

### 児童向け課題情報の返却

課題情報取得処理が返す情報は、課題名、問題スナップショット、実施に必要な設定、有効な出席番号一覧などに限定する。学校ID・内部クラスID・先生情報・他児童の履歴・クラス全体の成績は返さない。

### Attemptの無効化

Attemptは原則削除せず、`is_valid`等の状態で有効・無効を管理する。無効化時は`invalidated_at`、`invalidated_by`、`invalidation_reason`を記録する。通常の集計・CSVは有効なAttemptのみを対象にする。無効化操作は担当クラスの権限を持つ先生に限定し、サーバー側で権限を検証する。

### 出席番号の生成

クラス作成時に先生が人数を入力し、1から人数までの番号レコードを自動生成する。個別の有効／無効設定を許可する。同一年度・同一クラス内の番号重複をデータベース制約等で防ぐ。転出入・欠番等の運用詳細は試作時に確認する。

### RLS・アクセス制御

RLSを有効にし、先生向けのデータ取得・更新・CSV生成は認証済みユーザーと担当学校・クラスの権限をサーバー側で検証する。児童向けブラウザにはテーブルへの直接SELECT／INSERT権限を与えず、必要最小限のサーバー関数だけを公開する。`teacher.html`と`index.html`のファイル分離はアクセス制御の代替にならない。
