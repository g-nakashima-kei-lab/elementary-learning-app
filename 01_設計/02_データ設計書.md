# 100マス計算アプリ　データ設計書

**版：基本構想 v1.1**

## 1. データ設計の基本方針

全国の学校で利用することを想定し、学校ごとにデータを分離する。

データは、学校・先生・クラス・問題セット・配布・児童・解答結果の関係で管理する。

重要なのは、画面に表示する名前や番号と、システム内部でデータを識別するIDを分けることである。

内部IDにはUUIDなどの重複しにくい識別子を使用する。

## 2. データの関係

```text
学校（School）
 ├─ 先生（Teacher）
 └─ クラス（Class）
      ├─ 児童（Student）
      └─ 配布（Assignment）
           ├─ 問題セット（ProblemSet）
           └─ 解答結果（Attempt）
                └─ 児童（Student）
```

先生は担当する学校・クラスの範囲で管理する。学校をまたいでデータを閲覧できないようにする。

## 3. 管理するデータ

### ① 学校（School）

| 項目 | 内容 |
|---|---|
| school_id | 学校の内部ID |
| school_name | 学校名 |
| school_type | 公立・私立など |
| created_at | 登録日時 |
| status | 利用状態 |

### ② 先生（Teacher）

| 項目 | 内容 |
|---|---|
| teacher_id | 先生の内部ID |
| school_id | 所属学校ID |
| email | ログイン用メールアドレス等 |
| display_name | 表示名 |
| role | 管理者・先生など |
| status | 利用状態 |

先生の認証情報やパスワードは、独自に平文で保存しない。認証サービスを利用する。

### ③ クラス（Class）

| 項目 | 内容 |
|---|---|
| class_id | クラスの内部ID |
| school_id | 所属学校ID |
| grade | 学年 |
| class_name | クラス名 |
| school_year | 年度 |
| created_at | 登録日時 |
| status | 利用状態 |

クラス名は学校ごとに重複する可能性があるため、クラス名だけで識別しない。

### ④ 児童（Student）

| 項目 | 内容 |
|---|---|
| student_id | 児童の内部ID |
| class_id | 所属クラスID |
| attendance_number | クラス内の出席番号 |
| school_year | 在籍年度 |
| created_at | 登録日時 |
| status | 在籍・利用状態 |

当初は児童の氏名、メールアドレス、生年月日などを登録しない。児童はログインせず、クラスと出席番号を入力する。サーバー側では、class_id・school_year・attendance_numberの組み合わせで児童レコードを特定し、内部のstudent_idで結果を結び付ける。出席番号だけを全校共通の識別子として扱わない。同じ年度・クラス内で出席番号が重複しないよう制約を設ける。

クラスと出席番号は、学校内で児童を識別できる場合がある。氏名を保存しなくても個人に関係する情報として扱い、実際の児童データを使う前に必要な承認・安全対策を確認する。入力値のなりすましを完全には防げないため、児童入力は本人確認ではなく記録の紐付け手段と位置付ける。

### ⑤ 問題セット（ProblemSet）

| 項目 | 内容 |
|---|---|
| problem_set_id | 問題セットの内部ID |
| school_id | 作成した学校ID |
| created_by | 作成した先生ID |
| display_number | 画面に表示する問題セット番号 |
| operation | ＋・－・×など |
| grid_size | 5×5・10×10など |
| difficulty | 難易度 |
| generation_type | 共通・ランダムなど |
| problem_data | 問題内容または再現に必要な情報 |
| created_at | 作成日時 |
| version | バージョン |

表示番号が同じでも、内部IDが異なれば別の問題セットとして扱う。

### ⑥ 配布（Assignment）

| 項目 | 内容 |
|---|---|
| assignment_id | 配布の内部ID |
| school_id | 学校ID |
| class_id | 配布先クラスID |
| problem_set_id | 使用する問題セットID |
| teacher_id | 配布した先生ID |
| assignment_name | 配布名 |
| access_token | 児童用URLの識別情報 |
| snapshot_data | 配布時点の問題内容 |
| start_at | 開始日時 |
| end_at | 終了日時 |
| status | 公開・終了など |

配布は、問題セットとは別のデータとして管理する。

同じ問題セットを2つのクラスに配布する場合は、2つのAssignmentを作成する。

配布後に問題セットを編集しても、配布済みの問題内容は変わらないようにする。

### ⑦ 解答結果（Attempt）

| 項目 | 内容 |
|---|---|
| attempt_id | 解答記録の内部ID |
| school_id | 学校ID |
| class_id | クラスID |
| assignment_id | 配布ID |
| problem_set_id | 問題セットID |
| student_id | 児童ID |
| started_at | 開始日時 |
| completed_at | 終了日時 |
| elapsed_ms | 所要時間 |
| correct_count | 正解数 |
| total_questions | 問題数 |
| accuracy_rate | 正答率 |
| incorrect_count | 誤答数 |
| unanswered_count | 未回答数 |
| correction_count | 訂正回数 |
| created_at | サーバー受信日時 |

解答結果は原則として追加保存する。新しい結果で過去の結果を上書きしない。

同じ児童が同じ課題に複数回取り組んだ場合も、それぞれ別のAttemptとして記録する。

## 4. データの識別ルール

- 学校：school_id
- 先生：teacher_id
- クラス：class_id
- 児童：student_id
- 問題セット：problem_set_id
- 配布：assignment_id
- 解答：attempt_id

表示番号やクラス名、児童の出席番号だけでデータを結び付けない。

## 5. 児童ログインなしでの識別方法

第1段階では児童アカウントを作らず、児童はクラスと出席番号を入力する。先生が配布する課題URLでクラスをあらかじめ指定できる場合、児童の入力は出席番号のみとする案も採用候補とする。

1. 先生が年度・学年・クラスを登録する。
2. クラスの出席番号の範囲・在籍状況を設定する（氏名は初期版では登録しない）。
3. 児童は課題URLを開き、クラスと出席番号を入力する。
4. サーバーは対象課題・クラスに属する番号かを検証し、内部student_idに対応付ける。
5. 解答結果をAttemptとして保存する。
6. 同じ年度・クラス・出席番号の履歴を時系列で集約する。

出席番号の入力は本人確認ではない。他人の番号を入力できる可能性があるため、結果の訂正・再紐付け手順を用意する。児童用画面やAPIから、他の児童の履歴一覧を取得できない設計とする。

## 6. 学校間のデータ分離

全国で利用する場合、学校間のデータ分離は必須とする。

- すべての学校所属データにschool_idを持たせる。
- サーバー側でアクセス権限を確認する。
- 画面上で他校のデータを隠すだけの対策にしない。
- 先生が所属していない学校のデータを取得できないようにする。
- 児童用URLから取得できる情報を必要最小限にする。

## 7. 先生用の結果出力

先生が認証後、担当クラスの範囲で解答結果をCSV出力できるようにする。初期版ではCSVを優先し、Excel・Googleスプレッドシートに取り込みやすい文字コード（UTF-8 BOM等）とする。出力はサーバー側で先生の権限・対象クラスを確認してから生成する。児童用URLや児童側の画面からクラス全員分のデータを取得できないようにする。

出力項目候補：年度、学年、クラス、出席番号、課題名、実施日時、所要時間、正解数、問題数、正答率、誤答数、訂正回数。氏名は初期版では出力しない。

## 8. データ保存・削除方針

実装前に次のルールを決める。

- 学校が利用を終了した場合のデータの扱い
- 児童の転校・進級・クラス替えへの対応
- 出席番号の変更・転出入・進級時の履歴引継ぎ
- 解答結果の保存期間
- 先生の異動・退職時のアカウント管理
- 誤登録や不正アクセスが発生した場合の対応
- 学校からデータ削除を求められた場合の手順

保存期間は一律に決め打ちせず、学校・自治体のルールや利用目的を確認して定める。

## 9. 将来の拡張

将来、児童ログインを導入する場合も、AttemptやAssignmentの基本構造は維持できるようにする。

将来、正式な児童アカウントを導入する場合は、本人確認と既存履歴の安全な紐付け手順を設計する。

Google Classroom連携などを追加しても、問題セット・配布・解答結果の関係は維持する。
