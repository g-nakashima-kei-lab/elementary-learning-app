# 100マス計算アプリ　段階的な改修計画書

**版：開発ロードマップ v1.0**

## 1. 開発の基本方針

現在のアプリを活用しながら、全国の小学校で利用できる仕組みに段階的に発展させる。

一度に大規模な変更を行わず、各段階で動作確認と評価を行う。

現在の試行版は保存し、改修版と混在させない。

## 2. 現在のアプリの把握

これまでのコード監査報告によると、現在のアプリは次の構成である。

| 項目 | 現状 |
|---|---|
| 主なファイル | app.js / index.html / style.css |
| 文字認識関連 | stroke-recognizer.js |
| 問題の共有 | URLのtaskパラメータ |
| 問題の再現 | 条件・シード等を利用した決定的生成 |
| 学習履歴 | ブラウザのlocalStorage |
| 履歴保存数 | 最大50件 |
| 結果の集約 | 端末・ブラウザ内のみ |
| サーバー保存 | なし |
| 学校・クラス管理 | なし |
| 児童ID | なし |
| Google Classroom連携 | なし |

この内容は、現時点で共有された監査報告に基づく。改修を始める前に、実際の最新コードと照合する。

## 3. 開発の全体ロードマップ

| 段階 | 内容 | 目的 |
|---|---|---|
| 準備 | 現行版の保全・仕様整理 | 安全に開発できる状態にする |
| 第1段階 | サーバー保存・クラス自動集約 | 最初から結果を集約できるようにする |
| 第2段階 | 先生・学校・クラス管理 | 複数クラスで利用できるようにする |
| 第3段階 | 児童ごとの成長記録 | 継続的な学習状況を把握する |
| 第4段階 | 全国利用に向けた強化 | 学校間分離・運用・セキュリティを強化する |
| 第5段階 | 将来機能 | 個人ログイン・外部サービス連携など |

第1段階から、先生がクラス単位で結果を確認できることを必須とする。

## 4. 準備段階：現行版の保全

### 実施内容

- 現在のGitHubリポジトリを確認する。
- 現行版のコミットと動作環境を記録する。
- 現行版を別ブランチまたは別リポジトリで保全する。
- 画面・機能・問題生成・結果保存の仕様を整理する。
- 現行版で正常に動く操作をテスト項目にする。

### 注意点

現在の学校試行版を直接改修しない。新しい設計に基づく開発版を別に用意する。

### 完了条件

- 現行版に戻せる。
- 現行版の主要機能が確認できている。
- 改修版の作業場所が分離されている。

## 5. 第1段階：サーバー保存とクラス単位の自動集約

### 目的

児童が解いた結果をサーバーに保存し、先生がクラス単位で自動集約できる状態にする。

### 実施内容

1. バックエンド・データベースの候補を比較する。
2. 先生用の認証を実装する。
3. 学校・クラスの基本データを登録できるようにする。
4. 問題セットと配布を別々に管理する。
5. クラスごとに配布URLを発行する。
6. 児童の匿名IDを導入する。
7. 解答結果をサーバーに送信する。
8. 先生用画面にクラスの結果一覧を表示する。

### 先生用画面の最小構成

- クラス名
- 課題名・問題セット番号
- 取り組んだ児童数
- 解答回数
- 正答率
- 所要時間
- 児童ごとの結果一覧

### 児童用画面の方針

現在の計算画面・タイマー・結果表示など、既存の使いやすさをできるだけ維持する。

児童の操作を増やしすぎない。匿名IDの入力・選択方法は、実際の児童による操作テストを行って決定する。

### 完了条件

- 先生がログインできる。
- クラスを作成できる。
- クラス用の課題URLを発行できる。
- 児童がログインせずに取り組める。
- 結果がサーバーに保存される。
- 先生がクラス全体の結果を確認できる。
- 同じ児童の複数回の結果を区別して保存できる。
- 別の学校・クラスの結果を閲覧できないことを確認できる。

## 6. 第2段階：先生・学校・クラス管理

### 目的

複数の先生・クラス・学校で利用できるようにする。

### 実施内容

- 学校の登録・管理
- 先生の招待・登録
- 先生の担当クラス管理
- 学年・年度の管理
- クラスごとの問題セット管理
- 課題の公開・終了
- 問題セットの再利用

### 完了条件

複数の学校・先生が同時に利用しても、データが混在しない。

## 7. 第3段階：児童ごとの成長記録

### 目的

児童が継続して取り組んだ成果を把握できるようにする。

### 実施内容

- 児童ごとの履歴表示
- 正答率・所要時間の推移
- 前回との比較
- 自分の成長が分かる表示
- クラス全体の傾向表示

評価は単純な順位付けに偏らず、本人の前回からの変化を重視する。

## 8. 第4段階：全国利用に向けた強化

### 実施内容

- 学校ごとのデータ分離を再検証
- アクセス権限の監査
- 不正アクセス対策
- バックアップ・復旧手順
- データ保存期間・削除手順
- 利用規約・プライバシー関連文書
- 利用者向けマニュアル
- 費用・アクセス増加への対応

学校・自治体の情報セキュリティや個人情報の取り扱いに関する条件を確認し、実際の導入前に必要な承認を得る。

## 9. 第5段階：将来の拡張

- 児童ごとの正式なログイン
- Google Classroom連携
- 学年・学校単位の分析
- 問題セットの共有
- 教材の共同作成
- 学校外での利用

これらは、第1段階の安定稼働を確認してから検討する。

## 10. 技術選定で確認すること

バックエンドやデータベースは、次の観点で比較する。

| 評価項目 | 確認すること |
|---|---|
| 費用 | 試行段階と全国利用時の料金 |
| セキュリティ | 学校単位のデータ分離・権限管理 |
| 運用 | 保守や障害対応の負担 |
| 拡張性 | 利用校・児童数が増えた場合 |
| 開発のしやすさ | 現在のJavaScript資産を活用できるか |
| データ管理 | バックアップ・削除・移行の容易さ |

Supabaseなどを候補にするが、特定サービスに決めてから設計を合わせるのではなく、必要な設計要件を先に整理して選ぶ。

## 11. テストと安全対策

各段階で次のテストを実施する。

- 児童が問題を解いて結果を送信できる。
- 通信が切れた場合に結果が失われない、または再送できる。
- 同じ結果が重複登録されない。
- 同じ問題セットが正しく再現される。
- クラスごとに異なる問題セットを配布できる。
- 先生が自分の担当クラスだけを確認できる。
- 他校のデータにアクセスできない。
- 既存の計算・タイマー・入力機能が壊れていない。

## 12. 開発時のルール

- 変更前に現在のコードを確認する。
- 1回の改修で変更する範囲を絞る。
- 変更後は必ずテストする。
- 動作確認が終わるまで本番版を更新しない。
- Gitで変更履歴を残す。
- 不具合があれば直前の安定版に戻せるようにする。
- 児童の実データを使った試験は、必要な許可・安全対策を確認してから行う。

## 13. 最初に着手する作業

まずは、次の順番で進める。

1. 現行アプリの最新コードを保全する。
2. 現行機能とデータの流れを再確認する。
3. 学校・クラス・匿名ID・問題セット・配布・解答結果の関係を確定する。
4. バックエンド候補を比較する。
5. 小規模な試作環境を作る。
6. テスト用の先生・クラス・児童データで、結果の自動集約を確認する。

**最初の開発目標は、1つの学校・1人の先生・1クラスで、児童の結果が自動集約され、先生が一覧で確認できること。**

この最小構成が安定してから、複数クラス・複数学校へ広げる。
