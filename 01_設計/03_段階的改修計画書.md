# 100マス計算アプリ　段階的な改修計画書

**版：開発ロードマップ v1.3**

## 1. 開発の基本方針

現在のアプリを活用しながら、全国の小学校で利用できる仕組みに段階的に発展させる。

一度に大規模な変更を行わず、各段階で動作確認と評価を行う。

現在の試行版は保存し、改修版と混在させない。

## 2. 現在のアプリの把握

これまでのコード監査報告によると、現在のアプリは次の構成である。

| 項目 | 現状 |
|---|---|
| 主なファイル | app.js / index.html / style.css |
| 文字認識関連 | stroke-recognizer.js |
| 問題の共有 | URLのtaskパラメータ |
| 問題の再現 | 条件・シード等を利用した決定的生成 |
| 学習履歴 | ブラウザのlocalStorage |
| 履歴保存数 | 最大50件 |
| 結果の集約 | 端末・ブラウザ内のみ |
| サーバー保存 | なし |
| 学校・クラス管理 | なし |
| 児童ID | なし |
| Google Classroom連携 | なし |

この内容は、現時点で共有された監査報告に基づく。改修を始める前に、実際の最新コードと照合する。

## 3. 開発の全体ロードマップ

| 段階 | 内容 | 目的 |
|---|---|---|
| 準備 | 現行版の保全・仕様整理 | 安全に開発できる状態にする |
| 第1段階 | サーバー保存・クラス自動集約 | 最初から結果を集約できるようにする |
| 第2段階 | 先生・学校・クラス管理 | 複数クラスで利用できるようにする |
| 第3段階 | 児童ごとの成長記録 | 継続的な学習状況を把握する |
| 第4段階 | 全国利用に向けた強化 | 学校間分離・運用・セキュリティを強化する |
| 第5段階 | 将来機能 | 個人ログイン・外部サービス連携など |

第1段階から、先生がクラス単位で結果を確認できることを必須とする。

## 4. 準備段階：現行版の保全

### 実施内容

- 現在のGitHubリポジトリを確認する。
- 現行版のコミットと動作環境を記録する。
- 現行版を別ブランチまたは別リポジトリで保全する。
- 画面・機能・問題生成・結果保存の仕様を整理する。
- 現行版で正常に動く操作をテスト項目にする。

### 注意点

現在の学校試行版を直接改修しない。新しい設計に基づく開発版を別に用意する。

### 完了条件

- 現行版に戻せる。
- 現行版の主要機能が確認できている。
- 改修版の作業場所が分離されている。

## 5. 第1段階：サーバー保存とクラス単位の自動集約

### 目的

児童が解いた結果をサーバーに保存し、先生がクラス単位で自動集約できる状態にする。

### 実施内容

1. バックエンド・データベースはSupabaseを第一候補として、料金・セキュリティ・学校での利用条件を比較検証する（正式採用は保留）。
2. 先生用認証はメールアドレス＋パスワード方式を第一候補として試作する。Google認証は学校アカウントの制約を確認してから判断する。
3. 学校・クラスの基本データを登録できるようにする。
4. 問題セットと配布を別々に管理する。
5. クラスごとに推測困難なトークンを含む配布URLを発行し、DBにはトークンのハッシュ値を保存する。
6. 児童はログイン不要とし、課題URLからクラスを自動判定する。計算開始前に、画面上の出席番号ボタンから自分の番号を選択する。クラス人数の入力から1〜人数の番号を自動生成し、必要に応じて先生が個別に有効／無効を設定できる。
7. 解答結果はサーバー関数（Supabase Edge Functionを第一候補）を経由して検証・保存する。児童ブラウザからAttemptテーブルへの直接INSERTは許可しない。
8. 先生用画面（teacher.html）にクラス・課題の結果一覧を表示し、誤記録を無効化できるようにする。
9. 選択した課題単位で、出席番号順・UTF-8 BOM付きのCSVを出力する。

### 先生用画面の最小構成

- クラス名
- 課題名・問題セット番号
- 取り組んだ児童数
- 解答回数
- 正答率
- 所要時間
- 児童ごとの結果一覧
- クラス結果のCSV出力（Excel・Googleスプレッドシートで利用可能）

### 児童用画面の方針

現在の計算画面・タイマー・結果表示など、既存の使いやすさをできるだけ維持する。

児童の操作は、課題URLを開き、計算開始前に出席番号ボタンをタップする方式とする。課題URLからクラスを自動判定し、番号ボタンは対象クラスで有効な番号だけを表示する。児童の番号選択は本人確認ではないため、なりすましや入力間違いへの対応を設計する。

### 完了条件

- 先生がログインできる。
- クラスを作成できる。
- クラス用の課題URLを発行できる。
- 児童がログインせずに取り組める。
- 結果がサーバーに保存される。
- 先生がクラス全体の結果を確認できる。
- 同じ児童の複数回の結果を区別して保存できる。
- 先生が選択した課題単位の結果を、出席番号順・UTF-8 BOM付きCSVで出力し、Excel等で利用できる。
- 先生が誤記録を削除せず無効化でき、無効記録が通常の集計・CSVから除外される。
- 児童からの直接INSERTを禁止し、サーバー関数が課題トークン・出席番号・解答データを検証する。
- 別の学校・クラスの結果を閲覧できないことを確認できる。

## 6. 第2段階：先生・学校・クラス管理

### 目的

複数の先生・クラス・学校で利用できるようにする。

### 実施内容

- 学校の登録・管理
- 先生の招待・登録
- 先生の担当クラス管理
- 学年・年度の管理
- クラスごとの問題セット管理
- 課題の公開・終了
- 問題セットの再利用

### 完了条件

複数の学校・先生が同時に利用しても、データが混在しない。

## 7. 第3段階：児童ごとの成長記録

### 目的

児童が継続して取り組んだ成果を把握できるようにする。

### 実施内容

- 児童ごとの履歴表示
- 正答率・所要時間の推移
- 前回との比較
- 自分の成長が分かる表示
- クラス全体の傾向表示

評価は単純な順位付けに偏らず、本人の前回からの変化を重視する。

## 8. 第4段階：全国利用に向けた強化

### 実施内容

- 学校ごとのデータ分離を再検証
- アクセス権限の監査
- 不正アクセス対策
- バックアップ・復旧手順
- データ保存期間・削除手順
- 利用規約・プライバシー関連文書
- 利用者向けマニュアル
- 費用・アクセス増加への対応

学校・自治体の情報セキュリティや個人情報の取り扱いに関する条件を確認し、実際の導入前に必要な承認を得る。

## 9. 第5段階：将来の拡張

- 児童ごとの正式なログイン
- Google Classroom連携
- 学年・学校単位の分析
- 問題セットの共有
- 教材の共同作成
- 学校外での利用

これらは、第1段階の安定稼働を確認してから検討する。

## 10. Phase 1の暫定方針

| 項目 | 方針 |
|---|---|
| 先生認証 | メールアドレス＋パスワードを第一候補として試作 |
| Google認証 | 将来候補。学校のGoogle Workspaceでの利用条件を確認 |
| バックエンド | Supabaseを第一候補として比較・試作。正式採用は保留 |
| 児童のクラス判定 | 推測困難な課題URLトークンをサーバーで照合 |
| 児童の番号入力 | 計算開始前に出席番号ボタンをタップ |
| 画面構成 | 児童用`index.html`、先生用`teacher.html` |
| CSV | 選択した課題単位、出席番号順、UTF-8 BOM付き |

画面ファイルを分離しても、先生用データの保護にはならない。認証・権限確認はサーバー側で実施する。ブラウザ側に秘密鍵やサービスロールキーを置かない。

## 11. 技術選定で確認すること

バックエンドやデータベースは、次の観点で比較する。

| 評価項目 | 確認すること |
|---|---|
| 費用 | 試行段階と全国利用時の料金 |
| セキュリティ | 学校単位のデータ分離・権限管理 |
| 運用 | 保守や障害対応の負担 |
| 拡張性 | 利用校・児童数が増えた場合 |
| 開発のしやすさ | 現在のJavaScript資産を活用できるか |
| データ管理 | バックアップ・削除・移行の容易さ |

Supabaseなどを候補にするが、特定サービスに決めてから設計を合わせるのではなく、必要な設計要件を先に整理して選ぶ。

## 12. テストと安全対策

各段階で次のテストを実施する。

- 児童が問題を解いて結果を送信できる。
- 通信が切れた場合に結果が失われない、または再送できる。
- 同じ結果が重複登録されない。
- 同じ問題セットが正しく再現される。
- クラスごとに異なる問題セットを配布できる。
- 先生が自分の担当クラスだけを確認できる。
- 他校のデータにアクセスできない。
- 既存の計算・タイマー・入力機能が壊れていない。

## 13. 開発時のルール

- 変更前に現在のコードを確認する。
- 1回の改修で変更する範囲を絞る。
- 変更後は必ずテストする。
- 動作確認が終わるまで本番版を更新しない。
- Gitで変更履歴を残す。
- 不具合があれば直前の安定版に戻せるようにする。
- 開発・動作確認では架空の学校名・児童データを使用する。実際のクラス・出席番号・学習結果を組み合わせて扱うことは、児童を識別し得る情報の取扱いとして慎重に扱う。
- 実際の児童が学校タブレットから利用し、結果をサーバーに保存する試験は、必要な学校・自治体の確認・承認と安全対策を済ませてから行う。

## 14. 最初に着手する作業

まずは、次の順番で進める。

1. 現行アプリの最新コードを保全する。
2. 現行機能とデータの流れを再確認する。
3. 学校・クラス・出席番号・問題セット・配布・解答結果の関係を確定する。
4. バックエンド候補を比較する。
5. 小規模な試作環境を作る。
6. テスト用の先生・クラス・児童データで、結果の自動集約を確認する。
7. 先生用画面からCSV出力し、Excel・Googleスプレッドシートで正しく開けることを確認する。
8. 先生認証はメールアドレス＋パスワードを第一候補に試作し、Googleアカウント連携は学校アカウントの制約を確認して比較する。
9. Supabaseを第一候補として、無料枠・有料時の料金、データ保管条件、アクセス制御、バックアップを確認する。
10. 児童画面・先生画面を分離し、先生用APIのサーバー側権限検証をテストする。
11. 出席番号の誤選択、課題URLトークンの失効、通信失敗・再送、CSVの文字化けをテストする。

**最初の開発目標は、1つの学校・1人の先生・1クラスで、児童の結果が自動集約され、先生が一覧で確認できること。**

この最小構成が安定してから、複数クラス・複数学校へ広げる。


## 15. v1.3で確定したPhase 1の追加方針

### 15-1. 解答送信アーキテクチャ

- 児童用ブラウザからAttemptテーブルへの直接INSERTは許可しない。
- サーバー関数を経由して、課題トークン・課題状態・出席番号・解答データを検証してから保存する。
- Supabase Edge Functionを第一候補とする。RPCを採用する場合は、実行権限・RLS・SECURITY DEFINERの安全性を別途レビューする。
- サービスロールキー等の秘密情報はサーバー環境にのみ置く。
- レート制限、入力値検証、submission_id等による重複送信対策を設ける。

### 15-2. 児童向けAPIの返却範囲

児童用の課題情報取得処理は、課題名、問題スナップショット、必要な設定、有効な出席番号一覧だけを返す。他児童の履歴・クラス全体の成績・先生情報・内部ID等は返さない。

### 15-3. 出席番号の初期生成

先生がクラス人数を入力すると1から人数までの出席番号を自動生成する。欠番等に対応するため、生成後の番号を個別に有効／無効へ変更できる。

### 15-4. 誤記録の無効化

先生は担当権限の範囲でAttemptを削除せず無効化できる。無効化理由・日時・操作した先生IDを記録し、通常の集計・CSVから除外する。別児童への再紐付けUIはPhase 1では実装せず、必要時は管理者の個別対応とする。

### 15-5. CSV項目の統一

CSV項目は3設計書で統一し、年度、学年、クラス、出席番号、課題名、問題セット（表示番号または識別用名称）、実施日時、所要時間、正解数、問題数、正答率、誤答数、訂正回数とする。氏名は含めず、無効化されたAttemptは通常出力から除外する。形式は出席番号順・UTF-8 BOM付きとする。

### 15-6. 実装前の確認事項

Supabaseの無料枠・有料プランの料金と制限、停止条件、バックアップ、データ保管場所・リージョン、学校ネットワークからの接続可否、学校・自治体の利用条件を調べる。これらの確認と必要な承認が終わるまでは、架空データのみで開発し、実際の児童データや学校管理端末を使った試験は行わない。Supabaseのプロジェクト作成・契約は、費用と条件を確認して別途明示的に判断する。
